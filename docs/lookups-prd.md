# PRD: Backend-Driven Lookup System

**Owner:** Xu (Product Manager) · **Status:** Draft for review · **Scope:** `apps/web`, `mobile/*`, `packages/api`, `packages/db`, `packages/domain`, `packages/services/*`
**Doc type:** Simple PRD (no market or competitor analysis)

---

## 1. Product goal and context

**Goal.** Make the backend the single source of truth for every select, dropdown and enumerated "type" field, so an option is defined, labelled, ordered and retired in one place and every surface shows the same thing.

**Context.** The platform already has `lookup_types` and `lookups` tables, a repository, eight API procedures and a 23-type bilingual catalog, but **no screen uses them**: 134 UI sites in web and mobile ship inline option arrays or free-text "type" inputs, and the two client helpers that do exist (`apps/web/src/utils/lookups.ts`, `mobile/shared/.../lookups/Lookups.kt`) are imported by nothing but their own tests. The cost is already visible as data corruption: the trip wizard submits `day_trip` while `TRIP_CATEGORY` seeds `DAY_EXCURSION`; sign-up uploads send `insurance_certificate` and `vehicle_registration` while `DOCUMENT_TYPE` seeds `VEHICLE_INSURANCE`; `APPLICATION_STATE` rows store `Submitted` while callers compare `submitted` / `changes_requested`. Roughly 30 enum types the product needs are missing from the catalog entirely. Separately, the current design hides drift instead of surfacing it: the repository silently falls back to a hardcoded in-code catalog whenever the table is empty, so a broken deployment looks healthy, and there is **no active/inactive flag** — only soft-delete — so an option can only be retired by destroying history.

## 2. Personas and consumers

| Consumer                                                                     | Uses lookups for                                                                                                       | Failure that hurts them most                                                     |
| ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| **Traveler web** (`surfaces/traveler`)                                       | Trip category, cancellation reason, language, country, consent type                                                    | A saved preference that silently disappears, or a category that cannot be booked |
| **Organization dashboard** (`surfaces/business`)                             | Application state, document type, staff assignment source, supplier status, payout method, org permission areas/levels | Filters that disagree with the admin console, so counts do not reconcile         |
| **Admin console** (`surfaces/admin`)                                         | Everything above, plus dispute, settlement, reconciliation, refund decision, appeal decision, data-request types       | Being unable to retire a bad option without deleting records that reference it   |
| **Mobile: traveler, driver, photographer, moderator** (KMP, `mobile/shared`) | Same fields as their web counterparts, plus driver-run state, seat state, incident category                            | A value written on web that renders as a blank or a crash on a phone             |
| **Backend services** (`packages/services/*`)                                 | Validating incoming codes on write, resolving labels for notifications, invoices and exports                           | Bad codes entering the database and only being noticed months later              |

## 3. User stories

1. **As a traveler**, I want the trip categories in the booking wizard to come from the server, so that I only ever see categories that can actually be booked.
2. **As an organization administrator**, I want my application-state filter to use the same option list as the admin console, so that my counts match what platform staff see.
3. **As a platform administrator**, I want to deactivate a lookup value without deleting it, so that records that already reference it keep their meaning while nobody can pick it again.
4. **As a traveler**, I want my previously saved choice to still show its label when that option has been retired, so that I do not lose data or see a blank field.
5. **As an organization employee**, I want a clear message and a retry action when the options cannot be loaded, so that I know the field is unavailable rather than assuming the list is genuinely empty.
6. **As a driver on the mobile app**, I want the same option codes and labels as the web dashboard, so that a value set on web is readable and editable on my phone.
7. **As a backend service**, I want to reject an unknown or retired code on write, so that invalid values cannot enter the database through any surface.
8. **As an engineer on this repo**, I want the build to fail when someone adds a hardcoded options array or an unregistered lookup type, so that drift cannot be merged rather than being caught in review.
9. **As a platform administrator**, I want to reorder values within a type, so that display order reflects business priority identically on web and mobile.

### 4.2 Endpoints and error semantics

Five read procedures, all public and cacheable, all accepting and returning **codes only**:

| ID    | P   | Requirement                                                                                                                                                                                                                                                                                                   | Acceptance criteria                                                                                                                                                                                                                                                                                                            |
| ----- | --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| LK-08 | P0  | `listTypes` — list types, optionally filtered by `codes[]` or `parentCode`. Returns `{ types: [{ code, name{ar,en}, description, parentCode, sortBy, isActive, itemCount }] }`. Filters naming an unknown code return fewer types, never an error.                                                            | Request with 2 known + 1 unknown code returns exactly 2 types. `itemCount` counts active, non-deleted items only. Response is ordered by `sortBy`, `code`.                                                                                                                                                                     |
| LK-09 | P0  | `getTypeByCode` — one type plus its ordered active items: `{ type: {...}, items: [{ code, name, description, parentCode, sortBy, isActive }], status }`. `status` ∈ `ok` \| `type_not_found` \| `not_seeded`.                                                                                                 | Unknown code returns HTTP 200 with `type: null, status: "type_not_found"` (not a 404). A type with only inactive items returns `status: "ok"` and `items: []`, distinguishable from a missing type.                                                                                                                            |
| LK-10 | P0  | `getByTypeCodes` — batch form of LK-09 keyed by `typeCode`, so one page with 12 fields makes one request. Missing codes are simply absent from the map; `status` is per key.                                                                                                                                  | 12 requested, 1 unknown → 11 keys present, the unknown key absent, no throw. Response order per type matches LK-02. Web and mobile both call this for multi-field forms.                                                                                                                                                       |
| LK-11 | P0  | `resolve` — resolve one stored value: input `{ typeCode, code }`, output `{ item \| null, status }` with `status` ∈ `active` \| `inactive` \| `deleted` \| `not_found` \| `type_not_found`. Used to render labels for values that are no longer in the option list.                                           | An inactive item resolves with `status: "inactive"` and its label. A soft-deleted item resolves with `status: "deleted"`. A code absent from the table returns `not_found` with `item: null`. Never throws for these four cases.                                                                                               |
| LK-12 | P0  | `validate` — verdict on one or many values: input `{ typeCode, codes[] }`, output `{ results: [{ code, valid, reason }] }`, `reason` ∈ `ok` \| `inactive` \| `deleted` \| `unknown_code` \| `unknown_type`. Returns HTTP 200 even when every value is invalid.                                                | A form submits a stale `day_trip` against `TRIP_CATEGORY` and receives `valid:false, reason:"unknown_code"` without a thrown error, so the UI can show a field-level message.                                                                                                                                                  |
| LK-13 | P0  | Error semantics are uniform: reads never throw for absent or empty data (they return a `status` discriminator); writes reject invalid input with a typed error from the shared error catalog carrying the field path and the offending code. Unknown status values must not be treated as success by clients. | Contract test asserts the five read procedures return 200 for every absent/empty/inactive permutation. Write tests assert a typed error code and the field path for `unknown_code`, `inactive`, `deleted`, and empty-label cases. A client test asserts an unrecognised `status` renders the error state, not the empty state. |

## 5. Fallback decision table (P0, both platforms)

Five cases. "Stored value" means the value already on the entity being edited.

| #   | Case                                                                                   | Select shows                                                                                                                                                                          | Stored value preserved?                           | Can the user save?                                                                                                               | Can the user pick it again?                                                  |
| --- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| a   | **Type missing / unknown `typeCode`** (`type_not_found`)                               | Control disabled, empty option list, inline notice: "Options unavailable for this field." Stored value, if any, shown as its raw `code` in a disabled entry.                          | Yes — never rewritten.                            | Only if the field is optional or a stored value is already present; a required empty field blocks save with a field-level error. | No.                                                                          |
| b   | **Type exists, zero active items** (`ok`, `items: []`)                                 | Control disabled, empty list, inline notice: "No options available yet."                                                                                                              | Yes.                                              | Same rule as (a): required + empty blocks save; optional or already-populated saves unchanged.                                   | No.                                                                          |
| c   | **Stored value points at an inactive or soft-deleted lookup** (`inactive` / `deleted`) | The stored item is shown as a **disabled, non-selectable entry** labelled `<label> (no longer available)`, resolved via `resolve` (LK-11). It is not silently dropped and not hidden. | Yes — round-trips unchanged on save.              | Yes, as long as the user does not touch the field. Re-selecting is impossible, so it can only be cleared, never re-picked.       | No. Once cleared it cannot be restored by picking; it is gone from the list. |
| d   | **Stored value is not in the lookup table at all** (`not_found`)                       | Disabled entry labelled `<code> (unknown value)`. No crash, no blank field, no silent substitution.                                                                                   | Yes, unless the user explicitly clears the field. | Yes if untouched (server allows unchanged values, LK-19). Any new value must validate.                                           | No. Emits the LK-23 counter so the drift is visible.                         |
| e   | **Options request fails** (network, 5xx, timeout)                                      | Last-known good label if cached, else the raw `code`; control disabled; retry action; error text "Could not load options." Empty and error are visually and semantically distinct.    | Yes — a failed fetch never clears the field.      | Yes if the field is untouched; editing that field is blocked until options load.                                                 | No, until a successful retry.                                                |

Cross-cutting rules: a field is never silently emptied, never silently re-mapped to another code, and never shows an option list that contradicts the server. Any state other than `ok` renders a visible, announced (not colour-only) message.

## 6. UI/UX notes

- **One select contract, two implementations.** Web `TeSelect` (`{ value, label }[]`, native `<select>`, keeps the platform picker on phones) and mobile `TeSelect` (`TeOption(value, label)`, Compose dropdown) receive identical inputs and expose identical states: `loading`, `ready`, `empty`, `error`, `stale-value`. Both are already present in the repo and only need the state plumbing, not a redesign.
- **Five visible states** per field: loading (skeleton, not an empty list), ready, empty (disabled + notice), error (disabled + retry), stale-value (value rendered as a disabled entry, per §5 c/d).
- **Inactive rendering rules:** never silently dropped (the user would think their data vanished), never re-selectable (that would defeat retirement), always marked with the reason, always still displayed as a real label from `resolve` when one exists.
- **Accessibility and locale:** RTL mirroring and both languages per existing rules; the inactive marker must be text, not colour or an icon alone. The disabled entry keeps its `aria-describedby`/semantics so screen readers announce why it cannot be chosen.
- **Forms:** validation is shown per field on submit, not on load, so a retired stored value never greets the user with a red error before they touch anything.
- **Admin:** deactivating a value shows a confirmation with its usage count, so the operator knows the blast radius before hiding an option that 400 records reference.

## 7. Scope boundary

**In scope:** enumerated values that represent domain state or classification, on all six surfaces, plus their admin management and the guard that keeps them backend-driven.

**Explicitly out of scope:**

1. **Presentational option lists** — chart time ranges, page sizes, sort orders, density toggles, tab sets, navigation menus, wizard step counts, aspect-ratio and zoom presets. These are UI configuration, not domain data; they stay in code and are covered by the LK-14 allowlist with a written justification.
2. **Entity-id pickers** — plans, programs, organizations, employees, vehicles, seats, trips, photographers. These are rows with their own endpoints, permissions and pagination; a select backed by a lookup table would be wrong and would duplicate those endpoints.
3. **Free-text fields** that are not enumerations (names, addresses, amounts, notes).
4. **Locale/currency data quality** — the catalog carries country and currency codes, but ISO data maintenance, exchange rates and money formatting are out of scope.
5. **Tenant-level overrides** (LK-27), audit trail (LK-26) and translation workflow — planned, not required for this release.

## 9. Definition of done

1. All P0 rows pass their acceptance criteria, with one automated test per criterion.
2. `bun run lookups:check` and `bun run services:check` pass on `main`; the guard demonstrably fails on a reintroduced hardcoded array.
3. Zero of the 134 surveyed sites build their own option array; the three known drift bugs (LK-21) are fixed and covered by end-to-end tests.
4. The five §5 cases are verified on web and on at least one KMP target with shared fixtures.
